# Показ лабораторной №2

## Перед показом

Открыть приложение, Adminer и Figma. В БД должны быть опубликованная,
удалённая звезда и один черновик. Текущие данные сохранены из предыдущей версии.
Проверить SELECT id, title, status, creator_id FROM stars ORDER BY id;
Действия при показе меняют данные: это уже работа приложения, а не тест.

## Скриншоты 1–2

В Adminer изменить статус выбранной опубликованной записи на Удален,
показать SELECT id, title, status FROM stars ORDER BY id;
Запомнить её ID; физически строка не удаляется.

## Скриншоты 3–10

1. Открыть каталог, выбрать дату из существующих записей, нажать «Найти».
2. Показать сохранённую дату в поле и параметр received_date в URL.
3. Удалить свою опубликованную звезду кнопкой в каталоге.
4. Открыть /feed?id=ID_УДАЛЕННОЙ — ответ 404.
5. Если уже есть черновик, сначала заполнить его и опубликовать.
6. На /draft без черновика заполнить название, выбрать фото и видео, нажать «Далее».
   Файлы выбираются локально, у file-input нет name, в запрос не включаются.
7. В Adminer показать новую строку: статус Черновик, URL пустые,
   created_at заполнено, formed_at пусто.
8. Заполнить описание, дату и число планет, нажать «Опубликовать».
9. Показать в БД статус Опубликован и formed_at.

Network показывает POST с полями формы, ответ 303 и следующий GET.

## Скриншоты 11–13

В Adminer изменить дату и число планет опубликованной звезды, обновить приложение.
В таблице likes добавить или удалить строку через интерфейс Adminer
с действительными user_id и star_id; показать изменившееся число лайков.

~~~sql
SELECT s.id, s.title, s.received_date, s.habitable_planets,
       COUNT(l.id) AS likes_count
FROM stars AS s LEFT JOIN likes AS l ON l.star_id = s.id
GROUP BY s.id ORDER BY s.id;
~~~

## Скриншоты 14–21

Показать модели из models/, затем шесть обработчиков api/handlers.py:
пять используют ORM, удаление использует text("UPDATE ...") и параметры через

Показать db/session.py, настройки без демонстрации пароля и миграцию Alembic.

## ER-диаграмма

Открыть stars.mdj в StarUML. Три таблицы и три связи 1:N:
users → stars, users → likes, stars → likes.
Связь пользователей и звёзд по лайкам — M:N через likes.
Каскадное удаление запрещено, FK используют RESTRICT.
У stars частичный уникальный индекс на creator_id при статусе Черновик.
Длины указаны у VARCHAR; INTEGER, DATE, TEXT, TIMESTAMPTZ не имеют длины VARCHAR.
Формат подготовлен по официальному примеру:
https://github.com/staruml/staruml-samples/blob/main/ERDExample.mdj

## Коротко к контрольным вопросам

- PostgreSQL — реляционная СУБД: таблицы связаны первичными и внешними ключами.
- SELECT читает, INSERT добавляет, UPDATE изменяет, DELETE физически удаляет.
  Здесь удаление логическое: UPDATE статуса.
- ORM сопоставляет строки таблиц объектам Python. Session — единица работы с БД;
  commit фиксирует транзакцию, rollback отменяет.
- Курсор выполняет SQL и позволяет получать строки результата. В методичке
  Raw SQL передаётся через SQLAlchemy text и execute асинхронному драйверу.
- Модель описывает структуру данных; миграция — версионированное изменение схемы.
  stamp только отмечает версию, upgrade выполняет миграции.
- async/await позволяет отдавать управление во время ожидания БД или HTTP.
- Разделение слоёв: конфигурация, подключение БД, модели, обработчики, шаблоны.
  Полноценный слой сервисов и репозиториев в этой лабораторной не введён.
