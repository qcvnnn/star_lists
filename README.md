# Звёздные системы — лабораторная №3

REST API для каталога звёздных систем: просмотр, фильтрация, создание черновика с медиа, публикация, логическое удаление и лайки. Данные хранятся в PostgreSQL, файлы — в MinIO. Работа с БД выполняется через SQLAlchemy ORM.

## Технологии и файлы

FastAPI, Pydantic, SQLAlchemy AsyncSession, asyncpg, PostgreSQL, Alembic, MinIO Python SDK. Запросы проверяются в Postman.

| Файл / каталог | Назначение |
|---|---|
| main.py | Приложение, подключение роутера и статики |
| api/handlers.py | Все 10 HTTP-обработчиков, клиент MinIO и функция upload_file |
| schemas/api.py | Pydantic-схемы запросов и ответов |
| core/current_user.py | Фиксированный пользователь: общий словарь id=1 и get_current_user() |
| core/config.py | Настройки из .env |
| db/base.py, db/session.py | Базовая ORM-модель, движок и сессии БД |
| models/ | Модели User, Star, Like |
| data/media.py | Преобразование имени файла в ссылку и выбор статики для пустых значений |
| alembic/ | Миграции схемы БД |
| static/media/ | Изображение и видео по умолчанию |
| templates/ | Шаблоны предыдущих лабораторных; текущие API-методы их не рендерят |

## Запуск

Из папки проекта на текущем компьютере:

```shell
python -m pip install -r requirements.txt
docker start postgres minio_storage stars_adminer
python -m uvicorn main:app --reload
```

Контейнеры в этих командах уже должны существовать. PostgreSQL доступен приложению на localhost:5455. Adminer: http://localhost:8080 (сервер postgres, база stars_db). MinIO: http://localhost:9001 — консоль, http://localhost:9000 — API и файлы. Бакет media должен существовать и разрешать публичное чтение файлов по ссылкам.

Настройки подключения задаются в локальном .env, который не публикуется в Git:

```dotenv
DB_HOST=localhost
DB_PORT=5455
DB_USER=postgres
DB_PASSWORD=<пароль PostgreSQL>
DB_NAME=stars_db
CURRENT_USER_ID=1
MINIO_ENDPOINT=localhost:9000
MINIO_ACCESS_KEY=<ключ доступа MinIO>
MINIO_SECRET_KEY=<секретный ключ MinIO>
MINIO_BUCKET=media
MINIO_PUBLIC_URL=http://localhost:9000
```

Фактический пользователь API задан в core/current_user.py, а не параметром CURRENT_USER_ID из .env. Функция get_current_user() возвращает один и тот же словарь, созданный при загрузке модуля. Обработчики получают его через Depends(get_current_user). Регистрация не переключает текущего пользователя. Вход и выход пока являются заглушками.

Для проверки версии миграций: `python -m alembic current`. Для применения подготовленных миграций: `python -m alembic upgrade head`. Таблица alembic_version служебная и не относится к трём предметным таблицам.

## HTTP API

Базовый адрес: `http://127.0.0.1:8000`. Префикс всех методов: `/api/star_list`.

| Метод | URL | Назначение | Успешный ответ |
|---|---|---|---|
| GET | /api/star_list/catalog | Опубликованные звёзды с фильтром | 200, массив StarRead |
| GET | /api/star_list/feed | Одна опубликованная звезда / следующая | 200, StarDetailRead |
| GET | /api/star_list/draft | Черновик текущего пользователя | 200, StarDetailRead |
| POST | /api/star_list/stars | Создание черновика и загрузка двух файлов | 202, пустое тело (текущий код) |
| PUT | /api/star_list/stars/{star_id}/publish | Публикация своего черновика | 200, пустое тело |
| DELETE | /api/star_list/stars/{star_id} | Логическое удаление своей звезды | 200, пустое тело |
| POST | /api/star_list/stars/{star_id}/likes | Установка или отмена лайка | 200, пустое тело |
| POST | /api/star_list/users | Регистрация | 201, UserRead |
| POST | /api/star_list/users/login | Заглушка входа | 200, пустое тело |
| POST | /api/star_list/users/logout | Заглушка выхода | 200, пустое тело |

Коды ответов приведены по текущей реализации. Создание звезды возвращает 202 после загрузки файлов и сохранения строки; для завершённого создания ресурса семантически корректен 201 Created.

### GET /api/star_list/catalog

Необязательный query-параметр received_date — дата получения в формате YYYY-MM-DD. Фильтр по точному равенству. Без параметра или с пустым значением возвращаются все опубликованные записи всех пользователей. Результат отсортирован по id. Если совпадений нет, возвращается [].

```text
GET /api/star_list/catalog
GET /api/star_list/catalog?received_date=2026-09-29
```

Тела запроса нет. Некорректная дата возвращает 422; текущий обработчик добавляет пояснение в detail.

### GET /api/star_list/feed

Query-параметры: id — необязательный целочисленный ID звезды; next — логическое значение, по умолчанию false.

```text
GET /api/star_list/feed
GET /api/star_list/feed?id=1
GET /api/star_list/feed?id=1&next=true
```

Без id выбирается первая опубликованная звезда по возрастанию id. С id выбирается указанная опубликованная звезда. При next=true выбирается следующая по id; после последней — первая. Если передать next=true без id, текущий код сначала выберет первую, затем следующую. При отсутствии подходящей записи — 404 с пустым телом. Тела запроса нет.

### GET /api/star_list/draft

Без параметров и тела. Возвращает единственный черновик пользователя из get_current_user(). Если его нет — 404 с пустым телом. Сам GET черновик не создаёт.

### POST /api/star_list/stars

Тело multipart/form-data. В Postman: Body → form-data; Content-Type с boundary формируется автоматически.

| Поле | Тип | Обязательность |
|---|---|---|
| title | Text, строка 1–100 символов | Да |
| image | File, изображение | Да |
| video | File, видео | Да |

Пример значения title: TRAPPIST-1. Фото и видео передаются файлами, не URL. upload_file генерирует имя через uuid4().hex, добавляет расширение и загружает содержимое в MinIO. В image_url и video_url записываются имена объектов. Статус Черновик и creator_id назначает сервер, created_at — БД. Остальные незаполненные поля остаются NULL.

Если пользователя нет или у него уже есть черновик, текущий код возвращает 404. Успех — 202 с пустым телом. Получить созданную запись можно через GET /api/star_list/draft.

### PUT /api/star_list/stars/{star_id}/publish

star_id — целочисленный ID в пути. Тело application/json:

```json
{
  "description": "Описание звёздной системы.",
  "received_date": "2026-09-29",
  "habitable_planets": 2
}
```

Все три поля обязательны; habitable_planets — целое число не меньше нуля. Обновляется только свой черновик. Сервер назначает статус Опубликован и formed_at в UTC. Если подходящего черновика нет — 404, при успехе — 200, оба ответа с пустым телом.

### DELETE /api/star_list/stars/{star_id}

star_id — целочисленный ID в пути. Тела нет. Только своя неудалённая запись переводится в статус Удален через ORM. Строка и файлы сохраняются. Нет подходящей записи — 404; успех — 200. Тело ответа пустое.

### POST /api/star_list/stars/{star_id}/likes

star_id — ID опубликованной звезды. Тело application/json:

```json
{"value": 1}
```

value=1 ставит лайк текущего пользователя, value=0 отменяет. Повторная установка не создаёт дополнительную строку через этот обработчик. Отмена удаляет строку likes физически. Если пользователя или опубликованной звезды нет — 404. При успехе — 200 с пустым телом. Количество лайков видно в ответах GET.

### POST /api/star_list/users

Тело application/json:

```json
{"username": "student_demo", "password": "demo123"}
```

username — обязательная строка 1–50 символов; password — обязательная строка 1–20 символов. Ответ 201, например:

```json
{"id": 7, "username": "student_demo"}
```

Пароль не возвращается в JSON. В текущем учебном варианте сохраняется обычной строкой; аутентификация не реализована. Проверки уникальности username в текущем обработчике и модели нет.

### POST /api/star_list/users/login и POST /api/star_list/users/logout

Параметров и обязательного тела нет. Обе заглушки возвращают 200 с пустым телом. Токены, сессии и переключение текущего пользователя не выполняются.

## Текущий пользователь: функция-singleton

В лабораторной №3 авторизация ещё не реализована. В core/current_user.py один раз при загрузке модуля создаётся общий объект с фиксированным ID пользователя:

```python
current_user = {"id": 1}


def get_current_user():
    return current_user
```

Каждый вызов возвращает тот же объект в пределах процесса приложения. Это простая реализация требуемого доступа к фиксированному пользователю через функцию-singleton; словарь в обработчиках не изменяется.

Пример использования в обработчике:

```python
@router.get("/draft", response_model=StarDetailRead)
async def open_draft(
    db: AsyncSession = Depends(get_db),
    current_user: dict = Depends(get_current_user),
):
    star = await db.scalar(
        select(Star).where(
            Star.status == "Черновик",
            Star.creator_id == current_user["id"],
        )
    )
    # Далее обработчик возвращает поля черновика или пустой ответ 404.
```

Depends(get_current_user) вызывает функцию и передаёт результат обработчику. Текущий пользователь используется для получения своего черновика, создания, публикации, удаления, лайков и вычисления is_owner в каталоге и ленте. Регистрация создаёт другого пользователя, но не меняет фиксированный ID.

## Бизнес-логика

- Каталог и лента возвращают только опубликованные звёзды; каталог не ограничивается записями текущего пользователя.
- POST создания назначает статус Черновик. У пользователя может быть не более одного черновика.
- PUT публикации переводит свой Черновик в Опубликован и заполняет formed_at. Возврата в черновик нет.
- DELETE переводит свою неудалённую звезду в Удален. Строка, медиафайлы и лайки сохраняются.
- Лайк ставится только опубликованной звезде от фиксированного пользователя. Значение 1 означает наличие лайка, 0 — его отмену.
- id, creator_id, status, created_at и formed_at не берутся из клиентского тела для изменения: их назначают БД и бизнес-логика.
- Все обращения API к предметным таблицам выполняются через SQLAlchemy ORM, включая логическое удаление.

## Сериализаторы и ответы

Роль сериализаторов выполняют Pydantic-схемы из schemas/api.py. Входные схемы проверяют и преобразуют данные запроса в Python-объекты. Выходные схемы определяют структуру JSON-ответов через response_model.

| Схема | Где используется | Поля / назначение |
|---|---|---|
| RegisterRequest | POST регистрации | username, password |
| PublishRequest | PUT публикации | description, received_date, habitable_planets |
| LikeRequest | POST лайка | value — целое число от 0 до 1 |
| UserRead | Ответ регистрации | id, username; без пароля |
| StarRead | Ответ каталога | Общие поля звезды, число лайков и признак владельца |
| StarDetailRead | Ответы ленты и черновика | Наследует StarRead и добавляет description |

Отдельная входная схема не нужна для каждого из десяти методов. Каталог и лента принимают параметры URL, удаление — ID в пути, создание — Form и UploadFile. GET черновика и заглушки входа/выхода не требуют тела. Параметры URL и формы проверяются по типам и ограничениям в сигнатурах обработчиков.

| Поле StarRead | Тип JSON | Смысл |
|---|---|---|
| id | integer | ID звезды |
| creator_id | integer | ID создателя |
| title | string | Название |
| image_url | string | Ссылка на изображение |
| video_url | string | Ссылка на видео |
| received_date | string или null | Дата YYYY-MM-DD |
| habitable_planets | integer или null | Число планет в зоне обитаемости |
| likes_count | integer | Число строк likes для звезды |
| is_owner | integer | 1, если создатель — текущий пользователь, иначе 0 |

StarDetailRead содержит все поля StarRead и description (string или null). Он используется лентой и черновиком. Каталог возвращает массив StarRead. Поля с пустыми значениями сохраняются в ответе как null. Статус записи в JSON не передаётся.

Входные схемы не дают изменять системные поля: обработчики присваивают только явно перечисленные поля. Лишние JSON-поля игнорируются стандартным поведением Pydantic. Неверный формат входных данных может возвращать стандартный ответ FastAPI 422 с detail. Это отличается от пустых 404, явно возвращаемых обработчиками.

## Таблицы PostgreSQL

Три предметные таблицы: users, stars, likes. NOT NULL означает обязательное значение в БД. Все id — INTEGER, PRIMARY KEY, GENERATED BY DEFAULT AS IDENTITY.

### users

| Поле | SQL-тип | NULL | Назначение |
|---|---|---|---|
| id | INTEGER | Нет | Первичный ключ, назначается автоматически |
| username | VARCHAR(50) | Нет | Имя пользователя |
| password | VARCHAR(20) | Нет | Пароль учебного пользователя |

### stars

| Поле | SQL-тип | NULL | Назначение |
|---|---|---|---|
| id | INTEGER | Нет | Первичный ключ |
| title | VARCHAR(100) | Нет | Название звёздной системы |
| description | TEXT | Да | Описание |
| status | VARCHAR(20) | Нет | Черновик / Опубликован / Удален; по умолчанию Черновик |
| image_url | VARCHAR(2048) | Нет | Имя изображения в MinIO; старые записи могут содержать готовый URL или путь статики |
| video_url | VARCHAR(2048) | Нет | Имя видео в MinIO; старые записи могут содержать готовый URL или путь статики |
| received_date | DATE | Да | Дата получения — поле по теме и фильтр каталога |
| habitable_planets | INTEGER | Да | Число планет в зоне обитаемости |
| created_at | TIMESTAMPTZ | Нет | Дата создания; по умолчанию now() |
| creator_id | INTEGER | Нет | Внешний ключ на users.id |
| formed_at | TIMESTAMPTZ | Да | Дата публикации, назначается обработчиком |

CHECK stars_status_check ограничивает допустимые статусы. Частичный уникальный индекс stars_one_draft_per_user по creator_id для статуса Черновик допускает не более одного черновика пользователя.

По умолчанию image_url=/static/media/default-star.jpg, video_url=/static/media/default-star.mp4. media_url сохраняет готовые ссылки и пути статики, дополняет имена объектов адресом MinIO и бакетом. Пустые значения заменяет статикой. Доступность непустых ссылок текущая функция не проверяет.

### likes

| Поле | SQL-тип | NULL | Назначение |
|---|---|---|---|
| id | INTEGER | Нет | Первичный ключ |
| user_id | INTEGER | Нет | Внешний ключ на users.id |
| star_id | INTEGER | Нет | Внешний ключ на stars.id |

likes связывает пользователей и звёзды отношением многие-ко-многим. Число лайков вычисляется через COUNT(likes.id), отдельного столбца likes_count нет. Уникального ограничения на пару user_id, star_id в текущей модели нет; повторный лайк проверяется в обработчике с блокировкой строк.

### Связи

- users.id → stars.creator_id: один пользователь создаёт 0..N звёзд; у каждой звезды один создатель.
- users.id → likes.user_id: у пользователя 0..N лайков; у каждого лайка один пользователь.
- stars.id → likes.star_id: у звезды 0..N лайков; каждый лайк относится к одной звезде.

Все внешние ключи используют ON DELETE RESTRICT: каскадное удаление не используется. Звёзды удаляются логически сменой статуса.

## Проверка в Postman

Сохранить коллекцию из десяти методов, перечисленных выше. Для демонстрации: получить каталог с фильтром, создать звезду с файлами, получить черновик, опубликовать, открыть ленту без id и с id&next=true, поставить и снять лайк, удалить свою звезду, зарегистрировать пользователя и вызвать две заглушки. Для каждого этапа использовать фактический id из GET черновика.

Изменения в Adminer можно проверить:

```sql
SELECT id, title, status, image_url, video_url, received_date,
       habitable_planets, creator_id, created_at, formed_at
FROM stars ORDER BY id;

SELECT id, user_id, star_id FROM likes ORDER BY id;
SELECT id, username FROM users ORDER BY id;
```

Запрос ленты с next=true и запрос без id — два вызова одного метода. В коллекции также сохраняются заглушки login и logout, поэтому всего десять методов.

Диаграмма классов для сдачи должна показывать два домена (звёзды и пользователи), их интерфейсы и методы, зависимости от моделей Star/User/Like, таблицы stars/users/likes и четыре страницы фронтенда. Страницы ленты, добавления, каталога зависят от домена звёзд; планируемая страница входа/регистрации — от домена пользователей. Лайки входят в домен звёзд. Все URL на диаграмме должны начинаться с /api/star_list.
